# ASAP7 comparison

Run the same layouts through gdscheck and the independent
[ASAP7 KLayout port](https://github.com/laurentc2/ASAP7_for_KLayout).
The port is a second reading of the manual, not the non-public Calibre reference
deck. Agreement here does not establish signoff parity.

## Run

Requires Python 3 (standard library only), Git, KLayout (tested with 0.30.2), and
a built gdscheck. The runner never downloads or modifies the reference checkout.

```sh
git clone https://github.com/laurentc2/ASAP7_for_KLayout.git /tmp/ASAP7_for_KLayout
git -C /tmp/ASAP7_for_KLayout checkout ef77f080381cab3993428492a3dcb41044c3f518
cargo build --release

# Entire corpus; saves reports, inputs, versions and logs in a persistent directory.
hardening/oracle-asap7.sh --pdk /tmp/ASAP7_for_KLayout --output /tmp/asap7-comparison

# A quick library comparison, or selected generated cases:
hardening/oracle-asap7.sh --pdk /tmp/ASAP7_for_KLayout --case standard_cells
hardening/oracle-asap7.sh --pdk /tmp/ASAP7_for_KLayout \
  --case routed_clean --case routed_bad

# An arbitrary layout and top cell:
hardening/oracle-asap7.sh design.gds.gz --top TOP --pdk /tmp/ASAP7_for_KLayout
```

`--gdscheck` / `GDSCHECK` selects the binary; `--klayout` / `KLAYOUT` selects
KLayout; `ASAP7_KLAYOUT` supplies the checkout when `--pdk` is omitted. `--tiles`
defaults to `20 7`. `--output` must be new or empty to prevent stale reports
masquerading as successful runs. Omitting it creates a persistent temporary directory.
The reference commit **and macro SHA-256** are checked, including local changes.
To update the reference, review its changes, update both pins in `compare.py`, and
rerun and review the corpus; do not silently replace the baseline.

Exit status 0 means execution and gdscheck's manual expectations/tile invariance
passed, even if the tools disagree. Status 1 means a regression, or an unresolved
comparison difference with `--strict`. Status 2 means a setup, execution or parsing
failure. `--strict` treats unmatched rule/locations and KLayout manual-expectation
failures as errors; differing marker counts alone are informational.

## Reading the output

`comparison.md` lists each rule's counts, unmatched locations, tile stability and
targeted manual verdicts. `comparison.json` retains the raw rule labels, marker
values, bounding boxes, per-tile results, input/binary hashes and tool versions.
Each case directory contains both `.lyrdb` reports, logs and the flattened GDS.
Open the GDS and reports in KLayout to inspect a discrepancy.

The input copy is flattened before either checker runs. The reference macro is
unchanged, including its hierarchical mode. This avoids comparing child-local
coordinates with top-cell coordinates or counting a repeated child only once.

The explicit aliases in `canonical()` handle the port's swapped GATE.S.2/S.3 labels,
SRAM ACTIVE area labels, concatenated output strings and grouped V4-V7 spacing
rules. LIG.S.4 and S.5 are grouped on both sides because the port emits them together.
Other combined rules stay distinct: the runner does not guess which constituent
rule produced a marker. Original labels are always retained in JSON.

Location comparison uses many-to-many **bounding-box overlap** within 0.25 nm,
one layout DBU, allowing for the gdscheck report's decimal rounding. Two walls can
match one edge pair. Equal counts at different locations remain a discrepancy.
Bounding boxes are a triage aid: a large polygon box may overlap an unrelated
marker, so matches are not proof of equivalent geometry. No exact one-to-one marker
equivalence is claimed. Tile invariance separately compares exact serialized
rule/bounding-box multisets, including duplicate markers. Unexpected non-unit
report multiplicity after flattening is rejected. Tagged/skipped/waived or
unlocated markers, malformed reports and checker failures are errors, never clean
results.

## Fixtures and coverage

- The existing BSD-3-Clause LVT library has each standard cell placed once under
  `ALLCELLS`. It covers real library geometry, including isolated filler-cell
  context effects. It does not exercise SRAM or upper routing comprehensively.
- `tests/data/asap7/generated/` contains 100 tiny, deterministic GDS files and
  `cases.tsv`, generated by `gen/asap7.rs`. Coordinates use the real process scale
  and 0.25 nm DBU; cases straddle 7 or 20 micrometre tile boundaries.
- SRAM cases put identical ACTIVE geometry outside, inside and crossing SRAMDRC,
  at 13.25/13.5/13.75 and 26.75/27/27.25 nm well spacing/enclosure. Both the ordinary
  and relaxed rule are asserted, including which must remain inactive. The crossing
  spacing cases have the marker over the half of ACTIVE facing the well; three
  `crossing_far` cases put it over the other half, where clipping ACTIVE at the
  marker would change the verdict.
- Further targets cover both SRAM SDT overlaps below/at/above 17 nm, absent and
  touching references, V0–V3 corner spacing with zero/one/two local end-caps, V1's asymmetric
  5/2 nm enclosure (including split axes and rotation), M4 width, and the
  length-conditioned M8 width at a 400 nm line length and one DBU short of it.
- `routed_clean` has three routed nets using M4-M9 and V4/V6/V8. `routed_exact`
  shortens one M9 end to leave exactly 20 nm around V8, and `routed_bad` 19.75 nm
  where 20 nm is required. The Rust test requires no violations on the clean
  example and exactly that enclosure violation on the bad one. These are synthetic
  routing examples, not a synthesized design.
- `sram_bank` is the unmodified hierarchical `srambank_32b` GDS from
  The OpenROAD Project's `asap7_sram_0p0`, revision
  `522eeccbccefcd66e61893fa1059df24d95e9f86` (BSD-3-Clause).
  Its original SHA-256 is
  `bb2fe4b912afaf42103cc5a7f190d508de246ae9b7a682888c82a9c2e31d71b2`.
  The compressed fixture retains all cells, SRAMDRC markers and original 0.25 nm DBU.
  Run it with `--case sram_bank`. It exercises actual array and peripheral geometry;
  findings are recorded for review, not assumed to be zero or treated as Calibre parity.
  Rust CI runs the bank's SDT deck at both tile sizes; the external runner uses the
  full suite. Flattening produces about 118 MiB, and the pinned KLayout port takes
  several minutes on this case.

The manifest specifies 97 targeted verdicts across nine distinct rules.
Untargeted incidental violations remain in the full report. Only targeted rows
count toward the agreement summary: a rule silent on a layout is not necessarily
implemented, and a clean standard-cell library cannot establish whole-PDK parity.
Rules omitted from either checker remain gaps even when both stay silent.

## Regenerate and test

```sh
cargo run --features dev-tools --bin gen-testdata -- --pdk pdks/asap7/pdk.yml
cargo test --test asap7
GDSCHECK_TILE_UM=7 cargo test --test asap7
python3 -m unittest discover -s hardening/asap7 -p 'test_*.py'
```

GDS and gzip timestamps are fixed, so regeneration is byte-for-byte reproducible.
The generated GDS fixtures and manifest are committed; regular Rust CI needs no
KLayout installation. The Python comparison machinery is tested in CI separately.
The external comparison is an explicit integration run, with known disagreements
documented in `hardening/reports/asap7/parity.md`. Expectations come from the manual
and must not be updated merely to match a checker's current output.

`sram-scope.tsv` inventories every implemented rule/check and its SRAM applicability.
The PDK documentation explains the convention-7 interpretation: whole-polygon
selection, positive-area marker overlap, both subjects outside for ordinary spacing,
and complete reference layers for enclosure/coverage. Rust regressions cover contact
boundaries, remote marker overlap, mixed spacing pairs and reference geometry. The
pinned KLayout port does not apply this default consistently, so further SRAM
disagreements are expected; fewer markers alone do not establish correctness.
